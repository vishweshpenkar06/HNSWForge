## Phase 3 — parameter sweep

Command: `java -cp hnswforge-eval/target/classes:hnswforge-core/target/classes dev.hnswforge.eval.Main sweep --dataset synthetic --n 10000 --m 8,16,32 --efc 100,200 --efs 20,40,80,160 --k 10 --out results/sweep_synthetic.csv`
Chart: `docs/charts/recall_vs_qps_synthetic.png` (generated by `scripts/plot_results.py`).

Selected points at n=10,000, dim=32, k=10:

| m | efConstruction | efSearch | recall@10 | QPS | build_s |
|---:|---:|---:|---:|---:|---:|
| 8 | 100 | 20 | 0.846 | 46,793 | 0.94 |
| 8 | 100 | 160 | 0.974 | 9,264 | 0.89 |
| 16 | 100 | 20 | 0.963 | 37,335 | 2.27 |
| 16 | 100 | 80 | 0.993 | 10,475 | 2.17 |
| 32 | 100 | 20 | 0.992 | 22,299 | 10.0 |
| 8 | 200 | 160 | 0.984 | 8,903 | 1.50 |

Analysis: `efSearch` is the strongest query-time knob — at m=8/efC=100, raising it from 20 to 160 lifts recall from 0.846 to 0.974 but costs about 5x QPS. Raising `M` from 8 to 16 at efSearch=20 lifts recall from 0.846 to 0.963 with only a modest QPS drop (46.8k to 37.3k), but build time more than doubles (0.94s to 2.27s); M=32 reaches 0.992 recall but build time jumps to 10s, so returns diminish sharply. Raising `efConstruction` from 100 to 200 gives a small recall gain (e.g. 0.974 to 0.984 at m=8/efSearch=160) while increasing build time by roughly 60%, with little effect on query QPS. Practical default: M=16, efC=200, efS=100-160.

## Phase 4 — optimization waterfall

All rows: n=100,000, dim=32, m=16, efConstruction=200, efSearch=100, k=10, one query thread, 200 queries × 5 timed passes (3 warmup passes), queries sampled near corpus vectors. Measured with `dev.hnswforge.bench.OptimizationBench`.

| Step | Configuration | build_s | QPS | recall@10 |
|---:|---|---:|---:|---:|
| 0 | Phase 2 baseline: object graph, scalar, degenerate heuristic | 52.35 | 3,262 | 0.9265 |
| 1 | Flat vectors + flat adjacency + epoch visited + scratch heaps (scalar, no prefetch) | 48.10 | 714 | 0.9995 |
| 2 | + SIMD distance kernels | 30.18 | 1,112 | 0.9995 |
| 3 | + off-heap vector storage (MemorySegment) | 38.42 | 981 | 0.9995 |
| 4 | + prefetch-friendly traversal (heap, SIMD, prefetch) | 29.08 | 1,203 | 0.9995 |
| 5 | Final combination: SIMD + off-heap + prefetch | 39.25 | 923 | 0.9995 |

**The >=3x search speedup target was NOT met.** Measured cumulative QPS change from the recorded baseline is 923/3262 = 0.28x. Reasons, stated plainly:

1. The Phase 2 baseline contained a correctness bug: its "heuristic" compared `dist(base, candidate)` rather than `dist(candidate, selected)`, degenerating to simple nearest-neighbor selection. That produced sparser graphs (average degree 12.5) which are cheaper to search but return worse results (recall 0.9265). Fixing the heuristic (spec Algorithm 4) produced dense, fully connected graphs (average degree 22.6, 100% reachable at layer 0) and recall 0.9995 at the same efSearch — at the cost of more distance computations per query. The baseline's QPS advantage is therefore partly an artifact of lower recall.
2. SIMD gave a real 1.56x QPS gain over the flat scalar implementation (714 to 1,112) and a 1.59x build-time gain (48.10s to 30.18s).
3. Prefetch batching added another ~1.08x on heap (1,112 to 1,203) and was the fastest configuration measured.
4. Off-heap storage was slower than heap at 100k vectors (981 vs 1,112 QPS) because FFM segment reads add overhead at this size; its value is avoiding GC pressure for much larger indexes, which is not demonstrated by this datapoint.

Quality improved at every step: recall never dropped below the previous row (it rose from 0.9265 to 0.9995 at step 1 and stayed there). Build time improved 52.35s to 29.08s (1.8x) at the best configuration.

**Zero-allocation check:** JMH `-prof gc` on `SearchBench.search` (10k vectors, k=10, efSearch=100, 1 fork, 1 warmup + 1 measurement iteration of 2s): `gc.alloc.rate.norm = 320.867 B/op`, well under the 1 KB/op target. The remaining allocation is the returned result list and its `SearchResult` records; paths, heaps, visited stamps and query buffers are reused via `ThreadLocal<SearchScratch>`.

JMH benchmarks: `DistanceBench` (scalar vs SIMD, dims 1..960, all metrics), `SearchBench`, `InsertBench`. Run with `./mvnw -pl hnswforge-bench -am verify`, then invoke `org.openjdk.jmh.Main` with the generated `META-INF/BenchmarkList`.

## Phase 5 — concurrency and persistence

Parallel build of 100,000 vectors (dim=32, m=16, efConstruction=200, synthetic uniform data, `addAll`):

| Threads | build_s | speedup vs 1 thread |
|---:|---:|---:|
| 1 | 74.23 | 1.00x |
| 2 | 44.46 | 1.67x |
| 4 | 31.94 | 2.32x |
| 8 | 27.93 | 2.66x |

The scaling is sublinear because insertion contends on striped neighbor-list locks and on the shared entry-point region.

Mapped load of a 1,000,000-vector index file (dim=32, 264,000,128 bytes): `open_s = 0.0776` (full write of the same file took 0.262s). This measures mapping/header validation only; the graph in that synthetic file has no edges, so query results are not comparable to a built index.

Stress tests (all passing): 8 threads insert 50,000 vectors with degree/self-loop/duplicate invariants intact; parallel and sequential builds agree on recall within 0.01; 4 inserting + 4 searching threads run for 10 seconds with no invalid ids or worker failures; a preemptive timeout detects deadlock.

Persistence: v1 round trip preserves results for 1,000 random queries; mapped load returns identical ids with distances matching within 1e-5 (the in-memory index uses SIMD float accumulation, the mapped reader uses the scalar kernel); corrupted magic, wrong version, truncated files and CRC mismatches raise `IndexFormatException`; a committed `v1` fixture loads.

### Honest reading of the numbers

- At essentially equal recall (0.9995), hnswlib delivers 14,401 QPS versus HNSWForge's 3,026 QPS at efSearch=10 and 4,760 QPS at efSearch=320 — a **3.0x to 4.8x gap**, not within 3x at the default setting. Build time is 0.93s versus 2.90s (3.1x).
- Lucene is faster (9k-11k QPS) but its recall is fixed at 0.9665 because Lucene exposes no query-time efSearch; HNSWForge reaches 1.0000 recall at lower QPS. This is a quality/speed tradeoff, not a clean like-for-like win for either side.
- pgvector at equal recall is roughly on par with HNSWForge (2,950 vs 3,026 QPS) but is much slower to build (8.90s vs 2.90s) and pays network/JDBC overhead per query.

### Where HNSWForge loses and why (evidence-based hypotheses)

1. **No native prefetch/autovectorization.** hnswlib is C++ with raw pointers, `-march=native` and compiler autovectorization; HNSWForge uses the incubator Vector API through Java array offsets with per-call bounds validation. Evidence: 3.0-4.8x QPS gap at equal recall and 3.1x build-time gap on the same machine and data.
2. **Denser layer-0 graph.** Correcting the heuristic raised average degree from 12.5 (Phase 2, degenerate) to 22.6 and full reachability, which improved recall from 0.9265 to 0.9995 but increases distance computations per candidate pop. Evidence: the Phase 2 sparse graph had higher QPS at lower recall ([waterfall](#phase-4--optimization-waterfall)).
3. **Per-neighbor validation and allocation on the query path.** Every candidate passes a published/tombstone atomic read and bounds check, and each query allocates a result list plus up to k `SearchResult` records. Evidence: JMH gc profile measured 320.867 B/op after heaps/visited/query buffers were made allocation-free; hnswlib allocates no per-query objects in its C++ loop.
4. **JIT warmup and GC.** The JVM requires warmup before reaching steady state and may trigger GCs during long query runs; native C++ is fast from the first query. Evidence: QPS varied 2,864-4,760 across efSearch values at constant recall, indicating measurement noise/JIT effects that are not present in the native baseline.

No settings were cherry-picked: all efSearch values from 10 to 320 are reported for every system that supports it.
